§1 · Plan

Write the analysis plan before looking at results

What the plan fixes

Exposures, outcomes, sample types, lag window, model, covariates, multiple-testing control, and what result counts as an effect. Later changes become dated deviations.

Why

Choices made after seeing the data can push false positives far above 5%, even without deliberate fishing [1, 2]. A fixed plan keeps hypothesis testing apart from hypothesis generation [3].

With Claude

Claude drafts, you edit and approve, then it codes. Exploring and planning before implementing avoids solving the wrong problem [4]. Anything outside the plan is labelled exploratory.

§2 · Checks that can fail

Wrong analysis code rarely crashes. It returns a plausible number.

Without a check it can run, Claude stops when the work looks done; with a pass/fail check it can test and fix its own work [4]. New analyses usually have no reference to compare against (the “oracle problem” [5]), so the checks have to be built, and each expected result is written down before the check runs.

§3 · Numbers from code

Claude writes and runs the code; the code computes every number

The rule

No value read off a spreadsheet or plot and reported. No conclusion beyond what the code computed. Each number traceable to the script, cell or table that made it.

Why

Reproducibility means recording how every result was produced and avoiding manual data handling [10]. A model can lose or misremember details as a long session fills its context [4]; rerun code cannot.

§4 · Data sources

Pin down files, versions and joins; read files faithfully

State the inputs

Which files, sheets and versions, and how they join. Raw data stay read-only; everything else is derived by scripts [9, 10].

Keep tokens intact

Some readers turn the text “NA” into missing and “01” into 1. Both can carry meaning.

Count every join

Row counts before and after each join; dropped or duplicated rows are reported, never absorbed.

§5–6 · Changes and small steps

Look for silent changes; build one step at a time

§5 When inputs change

A changed input fails loudly (a crash) or silently (different numbers, no error). Compare old and new values, find outputs not regenerated and rows that no longer join. Keep every output regenerable from code [10].

§6 Small steps, every figure

Load → describe → one model → one figure, checking each output. Short feedback loops and early correction work best [4]. Plots expose problems that summary numbers hide: Claude opens each figure before describing it.

§8–9 · Review and communication

A sceptical second pass; say what you mean

§8 Review in a fresh context

A reviewer in a separate session or subagent sees the work and the criteria, not the reasoning behind it [4]. Ask it for problems that affect correctness or the plan: a reviewer asked to find gaps will always find some, and chasing every one over-engineers [4].

§9 Be specific; expect questions

Name files, constraints and what “done” looks like [4]. Supply what only you know: biology, reviewers’ questions, which result would change a conclusion. Claude asks when a request has two readings, and states the one it chose.

§10–11 · Memory and safety

Memory in files; nothing that cannot be undone

§10 Project memory

Each new session starts blank. Durable rules go in a short, specific CLAUDE.md, read at every start [4, 24]; plan, decisions and status in a progress file. Start fresh sessions between tasks and after repeated failed corrections [4].

§11 Irreversible actions

Read-only raw data, regenerable outputs, version control and backups [9, 10]. Checkpoints undo Claude’s file edits but not shell commands [4]. Rules that must always hold go in hooks, which are deterministic; CLAUDE.md is advice [4].

§12 · Notebooks

A notebook counts only if it runs top to bottom

Hidden state

Interactive edits can leave results the saved code no longer reproduces [25]. Claude cannot see your kernel, so it reruns the whole notebook before reporting.

Code in modules

Reusable logic in .py modules; the notebook holds narrative, figures and decisions [25].

One parameters cell

Paths, cut-offs and seeds near the top; record software versions [10, 25].

Explain as you go

Each step says why, not only what; every output is labelled so it reads on its own [25].

The project

LONGIT-weeklong: three notebooks, in this order

COMPONENT 0

What is in the diet logs

Foods logged, live-microbe, fermented, fibrous and dairy foods, agreement with the questionnaire. Descriptive.

COMPONENT 1 · NOW

Is the diet log reflected in food sequencing?

trnL (plants) and 12SV5 (meat) DNA in stool, capsules and saliva vs what was logged: recall and precision.

COMPONENT 2 · NEXT

Does diet relate to 16S composition?

Live-microbe foods and fibre variety as primary exposures; plan written, not run.

Notebooks in scripts/ (component0_diet_logs, component1_foodseq_diet, component2_diet_16S); each writes to its own folder in figures/. Subject 11 has no diet log: left out of anything that uses it.

WHY

Food sequencing comes first because it tests whether the diet log is a trustworthy record of what reached the gut; component 2 uses the log as its exposure. The diet-log description is used by both, so it has its own notebook instead of being repeated.

Input reports and rule tests · workflow step 0

Know the data before every session

scripts/profile_inputs.py

One report per input in figures/input_profiles/: sheets, columns, every value of short categorical columns, tokens (NR, NM, NA), key uniqueness. joins.md: how well each documented join matches. manifest.json: checksums; changes.md says what changed.

scripts/tests/

68 pytest tests: one per CLAUDE.md file or join rule, plus the shared modules against earlier outputs. Breaking the saliva-time or meal rule on purpose makes exactly those tests fail.

If a checksum changed: compare with the report in previous/, classify each difference, rerun the tests, record it in PROGRESS.md, then analyse.

WHY

Claude starts each session knowing nothing about the data. Reports written by code give it an accurate picture without opening large workbooks; the tests show whether the written rules still hold. Checksums catch a changed input before it silently changes a result.

23 / 37 · joins

Matching rules

Meals, and which ASVs count for a food

Meal of an entry

  • Meal word first (breakfast, brunch, lunch, dinner)
  • Else first clock time: before 11:00 breakfast, to 15:59 lunch, then dinner
  • Bare 1:00–5:59 is pm; other bare times keep the day in time order
  • Nothing usable: “not recorded”

ASVs for an ingredient

  • Species from the lexicon; run from its marker
  • Epithet: ASVs with that label + unlabelled ASVs of the genus
  • No ASV carries the epithet, spp., hybrids: whole genus
  • Slash lists, higher taxa, “unspecified”: undetectable
  • Species whose ASVs overlap merge into one food taxon; a recipe (kimchi) joins each of its species

WHY

These rules used to exist only inside old code. A fresh session given only CLAUDE.md got 10 meals and 19 ingredients’ ASV sets wrong. Written out in full, they reproduce the old outputs exactly (58 of 58 meals, 60 of 60 ASV counts) and are now tested.

24 / 37 · rules

Food taxa and the naming check · component 1

What sequencing can tell apart, and what it cannot find

FOOD TAXA

Merged by shared sequences

Milk, cheese and beef are one taxon (Bos taurus); tomato, potato and eggplant one (Solanum). 116 logged foods form 68 taxa.

NAMING CHECK

Species first, then genus

Of 142 informative foods: 64 match the exact species, 25 the genus only, 27 need the congener fallback; 26 find nothing.

YES vs UNCERTAIN

Rated before sequencing

Yes: DNA expected (whole foods). Uncertain: processed, trace or low-DNA (egg, butter, coffee); a miss is not a false negative.

24 unmatched plant foods (corn, apple, cucumber, squash, strawberry, ...) have a genus absent from the trnL taxonomy (plus sardine in 12SV5; white fish names no taxon): most likely a reference-database gap, not a naming error.

WHY

Food names in the log and species names in the sequence database come from different worlds. Matching them explicitly, and showing every match, makes naming mistakes and database gaps visible instead of turning them silently into missed foods.

Write protection

Two layers for two ways of writing

LAYER 1 · FILE TOOLS

PreToolUse hook

Before every Write, Edit or NotebookEdit, restrict_writes.py checks the path. Outside scripts/, figures/ and PROGRESS.md the edit is cancelled and Claude is told why.

LAYER 2 · SHELL COMMANDS

Bash sandbox

Python, Jupyter, cp, rm and every other command run inside an operating-system fence. Writes elsewhere fail with “Operation not permitted”, child processes included.

WHY

A rule in CLAUDE.md is advice: in a long session it can be forgotten or misread. A hook and the sandbox are enforced by the software every time [4]. Two layers are needed because Claude can write through its own file tools or through any shell command, and each layer covers only one of them.

27 / 37 · protection

The Bash sandbox

A fence around every shell command

What it is

macOS sandboxing applied to each command Claude runs and everything it starts.

Files

Every protected file and folder is write-denied; scripts/, figures/ and a private temp folder stay writable.

Network

No internet; local ports allowed, which Jupyter kernels need.

Strict mode

A blocked command cannot be retried outside the fence; no sandbox, no start.

Self-protecting

.claude/ settings, hooks and agents are always write-denied.

WHY

Analysis scripts and notebooks run as shell commands and could write anywhere; only an operating-system fence stops a buggy script from overwriting data. Strict mode stops a blocked command from being quietly rerun unprotected, and the fence cannot be loosened from inside.

28 / 37 · sandbox

The sandbox covers shell commands only. Claude’s own file tools (Write, Edit) run outside it, which is why the hook exists as layer 1. Hooks themselves also run outside the sandbox.

.claude/settings.json

Three blocks: env, hooks, sandbox

"env": { matplotlib, Jupyter caches → temp },

"hooks": { "PreToolUse": [{

  "matcher": "Write|Edit|MultiEdit|NotebookEdit",

  "command": "python3 …/restrict_writes.py" }] },

"sandbox": { "enabled": true,

  "failIfUnavailable": true,

  "allowUnsandboxedCommands": false,

  "network": { "allowLocalBinding": true },

  "filesystem": { "allowWrite": [scripts, figures],

    "denyWrite": [ 1-data, CLAUDE.md, … 21 paths ] } }

env

Caches go to the sandbox’s temp folder, so notebooks run.

hooks

Path check before every file-tool write (layer 1).

sandbox

On, strict; each protected path listed, since a deny beats an allow.

WHY

Claude Code reads settings only from the folder a session starts in, so identical copies sit in gen2-longit/.claude/ and diet_log_analyses/.claude/. They live in .claude/, which the sandbox always protects, so only you can change them and Claude cannot loosen its own limits.

The reviewer agent

A read-only referee with a fresh context

The file

.claude/agents/reviewer.md: tools Read, Grep, Glob, Bash, no Write or Edit.

What it checks

Joins, denominators, leakage, repeated measures, FDR, whether checks really passed, over-claiming.

What it returns

Problems affecting correctness or the plan, each with evidence; minor points apart.

HOW TO CALL IT (WORKFLOW STEP 8)

Use the reviewer subagent on section 2 of scripts/<notebook>.ipynb

WHY

A reviewer that has seen the reasoning tends to accept it; one with a fresh context judges only the evidence [4]. It is read-only so a review cannot change the work it is judging, and asked for serious problems only so reviews do not turn into over-engineering [4].

Gotchas in these data

Things that silently go wrong

Excel reading

Plain pd.read_excel turns “01” into 1 and “NA” into missing. Use read_excel_like_readxl().

OTU ≠ Feature

Taxa follow the tree’s tip order, so feature_%04d names differ from feature_data’s Feature.

Unresolvable foods

Milk, cheese and beef are all Bos taurus: compare per food taxon, not per ingredient.

Uncertain foods

Egg is Gallus gallus but rated Uncertain: chicken DNA can look “never logged”.

Reference gaps

24 logged plant foods (corn, apple, squash…) have no genus in the trnL taxonomy.

Broad detection

At 0.1%, saliva and some stools carry many taxa; plant DNA is also in blanks.

WHY

Each of these has already produced a wrong or misleading result once without any error message. They are written into CLAUDE.md, PROGRESS.md or the notebooks so that new code handles them on purpose instead of rediscovering them.
